## 🎯 THE PROBLEM

You have **two different authentication flows** that need to work together:

### **Current MCP Service (CTERA AI)**
```
User → nginx → oauth2-proxy → Envoy → MCP Python Service
         ↓
    Validates JWT with IdP (ENTRA/Keycloak)
    Adds headers: X-Forwarded-User, X-Forwarded-Email
```

**Key characteristics**:
- ✅ Works with external IdP (ENTRA, Keycloak)
- ✅ Interactive login flow (user redirects to IdP)
- ✅ JWT signature validated by oauth2-proxy against IdP's public keys
- ❌ **NOT suitable for n8n** (n8n workflows are non-interactive!)

### **Desired n8n Flow (Non-Interactive)**
```
n8n Workflow → Portal Backend → MCP Python Service
         ↓
    Bearer token (JWT)
    No user interaction
    No IdP redirect
```

**Key characteristics**:
- ✅ Non-interactive (workflows run automatically)
- ✅ Long-lived tokens (60-90 days)
- ✅ Portal-generated JWTs (not external IdP)
- ❌ **oauth2-proxy won't work** (expects IdP validation)

## 💡 THE SOLUTION: Dual Authentication Path

We need **TWO parallel authentication mechanisms** for MCP:

### **Path 1: Interactive (CTERA AI) - KEEP AS-IS**
```
Claude Desktop / Browser
    ↓
nginx → oauth2-proxy (validates with IdP) → Envoy → MCP Service
    ↓
X-Forwarded-User header
```

**Use case**: Interactive AI assistants (Claude, ChatGPT, etc.)

### **Path 2: Non-Interactive (n8n, Automation) - BUILD THIS**
```
n8n / Automation Tool
    ↓
Portal Backend (validates Portal-generated JWT) → MCP Service
    ↓
UserPrincipal from JWT
```

**Use case**: Workflow automation, scheduled tasks, integrations

## 🏗️ IMPLEMENTATION STRATEGY

### **Option A: Bypass oauth2-proxy for Portal JWTs** ⭐ RECOMMENDED

**Architecture**:
```
┌─────────────────────────────────────────────────────────┐
│                    nginx (Routing Layer)                 │
│                                                           │
│  IF request has X-Portal-JWT header:                    │
│    → Route to Portal Backend (bypass oauth2-proxy)      │
│  ELSE:                                                    │
│    → Route to oauth2-proxy (IdP validation)             │
└─────────────────────────────────────────────────────────┘
                    ↓                    ↓
        ┌───────────────────┐   ┌──────────────────┐
        │  Portal Backend   │   │  oauth2-proxy    │
        │  (JWT Validator)  │   │  (IdP Validator) │
        └───────────────────┘   └──────────────────┘
                    ↓                    ↓
                ┌──────────────────────────┐
                │     Envoy → MCP Service  │
                └──────────────────────────┘
```

**nginx configuration**:
```nginx
location /mcp/ {
    # Check for Portal-generated JWT
    if ($http_x_portal_jwt != "") {
        # Bypass oauth2-proxy, go directly to Portal Backend
        proxy_pass http://portal-backend:8080;
        proxy_set_header Authorization "Bearer $http_x_portal_jwt";
        break;
    }
    
    # Otherwise, use oauth2-proxy for IdP validation
    auth_request /oauth2/auth;
    proxy_pass http://envoy:80;
}
```

**Portal Backend** (Java):
- Validates JWT using `JwtAuthorizationBearerValidator` (new, using jose4j)
- Extracts UserPrincipal from JWT
- Forwards request to MCP service via Envoy with user context

**Pros**:
- ✅ Clean separation of concerns
- ✅ No changes to oauth2-proxy or existing IdP flow
- ✅ Portal has full control over JWT validation
- ✅ Can add refresh tokens, revocation, scopes

**Cons**:
- ⚠️ Requires nginx configuration changes
- ⚠️ Two authentication paths to maintain

## 🔑 KEY INSIGHTS

### **Why oauth2-proxy can't handle Portal JWTs**:

1. **oauth2-proxy is designed for IdP integration**:
   - Expects OIDC discovery endpoint (`/.well-known/openid-configuration`)
   - Fetches public keys from IdP's JWKS endpoint
   - Validates JWT signature against IdP's keys
   - Handles refresh token flow with IdP

2. **Portal JWTs are self-issued**:
   - Portal is the issuer, not an external IdP
   - No OIDC discovery (Portal is not an IdP)
   - Uses HMAC-SHA256 (shared secret), not RS256 (public/private keys)
   - Refresh tokens managed by Portal, not IdP

3. **Architectural mismatch**:
   - oauth2-proxy: "Trust the IdP, validate against it"
   - Portal JWTs: "Trust the Portal, validate locally"

### **Why n8n can't use IdP flow**:

1. **Non-interactive**: Workflows run automatically, no user to redirect
2. **Long-lived**: Need 60-90 day tokens, IdP tokens expire in 1 hour
3. **No refresh**: n8n can't handle interactive refresh (would break workflows)
4. **Automation-first**: Designed for API keys, not user sessions
